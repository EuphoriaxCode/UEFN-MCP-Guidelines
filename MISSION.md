# Mission — become fluent in UEFN Scene Graph through a self-built CLI

*(Rewritten from the original request, Oct 2026. Give this file to any agent session that continues the work.)*

## Goal
Build, use and keep improving a command-line tool (`cli/uefn`) that drives **Unreal Editor for Fortnite** through its
MCP server, so an AI agent can design, build, test and debug ambitious UEFN systems — with a focus on the
**Scene Graph** (entities, components, prefabs, Verse components), because that is where agents are weakest today.

## How to work
1. **Start from what is known.** Read `MCP_RULES.md`, `topics/`, `catalog/`, `experiments/LOG.md` before touching the editor.
   Never re-test something already recorded unless the UEFN version changed — then note the version.
2. **Probe → small test → batch.** Use the CLI for every editor interaction. When a step is clumsy, improve the CLI first
   (new command, better error, helper) and then do the step.
3. **Run experiments, not guesses.** Every experiment gets an entry in `experiments/LOG.md`:
   goal → what was run (exact command/script) → result (worked / failed + the exact error) → lesson.
   **Failures are as valuable as successes — always write them down**, including editor crashes and what triggered them.
4. **Promote lessons.** A lesson that would have saved time goes into `topics/*.md`; a hard must-follow rule also goes into
   `MCP_RULES.md`. Mark anything not verified in a running game as *(unverified)*.
5. **Verify in the real thing.** Verse must build (`uefn build`), level changes must be read back (`uefn sg tree/dump`), visuals
   checked with `uefn shot`, runtime behaviour with a session + log lines (`uefn log LogVerse`).
6. **Commit often** with clear messages so the repo is always a usable snapshot. Don't break the user's existing projects:
   new work goes in new folders/files; scratch entities get deleted.
7. **Keep going.** After each finding, pick the next most valuable unknown from the backlog below (and add new unknowns
   you discover). Stop only when told to or when the usage budget runs out.

## What "fully crazy UEFN systems" needs (the backlog)
Everything below should end up either *proven* (with a recipe/example) or *proven impossible* (with the reason).

**Scene Graph authoring (editor, via MCP)**
- Full component atlas: every component class, its editable properties, which ones crash the editor.
- Declarative scene building: JSON spec → entity tree (idempotent apply, dump back, repeat/array patterns).
- Custom meshes generated by code → imported → used as mesh components with per-instance materials.
- Prefabs: create (or prove impossible), instantiate, override, propagate; prefab classes in Verse.
- Lights, text, decals, particles, sounds, cameras, keyframed movement, physics, interactables on entities.

**Scene Graph runtime (Verse)**
- Spawning/destroying entities and prefab instances at runtime; parenting/re-parenting.
- Transforms, origins, animation via keyframed movement and via Verse tweening.
- Overlap/sweep queries, collision profiles, tags and tag queries, scene events (SendUp/SendDown).
- Custom components talking to each other; per-frame ticking (`TickEvents`); interaction flows.
- Mixing devices with Scene Graph (devices find entities and vice versa).

**Pipeline & testing**
- Verse write/build loop, session start/push/restart, reading runtime logs, screenshots, self-test devices.
- Asset pipelines: meshes, textures, materials (+ instances and parameters), Niagara, data tables.

**Systems to prove the stack** (each one a folder in `examples/`)
- Procedural level generator, physics toys, animated machines, interactive UI-in-world, NPC/AI behaviours, minigames.

## Where things go
| Path | What |

| `examples/` | Working systems with Verse, build scripts/specs and screenshots |
